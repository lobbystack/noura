# Workspace format v1

A Noura workspace is a normal directory with its manifest at `.noura/workspace.yaml`. Markdown files with valid managed frontmatter become workspace objects. Other files remain ordinary files.

## Manifest

Noura keeps its own workspace-level files under `.noura` so the workspace root remains user content.

```yaml
id: workspace_01k...
format_version: 1
name: Example workspace
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
enabled_plugins:
  - folders
  - notes
  - tasks
  - calendar
  - projects
ignore: []
```

The workspace ID identifies the workspace across moves. Device-local indexes and credentials live in operating system application-data and credential directories.

`enabled_plugins` lists the identifiers of the modules the workspace turns on. Rules:

- Plugin identifiers are a lowercase letter followed by lowercase letters, digits, or hyphens, at most 64 characters total.
- Order is not significant, and writers deduplicate the list. Readers tolerate a hand edit's duplicates and unsorted entries by canonicalizing on read; writers serialize the deduplicated list in sorted order.
- An empty list is valid and enables no domain modules.
- Readers preserve unknown identifiers and ignore IDs they do not implement, so future ecosystem plugins do not break older builds.
- Application plugin toggles rewrite this file atomically and refresh `updated`.

## Managed Markdown

```markdown
---
id: task_01k...
type: task
status: todo
priority: medium
project: null
due: 2026-09-04
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
---

# Prepare release notes

Summarize user-visible changes.
```

IDs use a lowercase object-type prefix and lowercase ULID. Timestamps use RFC 3339 UTC. The serializer accepts `YYYY-MM-DD` for all-day date properties or RFC 3339 with an explicit offset for timed values.

The serializer writes known fields in canonical order and sorts unknown properties by key. It preserves unknown JSON-compatible values. It does not preserve YAML comments, aliases, tags, or the original formatting after an application mutation.

## Classification

- A file with valid `id` and `type` fields becomes a managed object.
- Idless Markdown remains unmanaged until explicit adoption.
- Malformed frontmatter remains untouched and searchable as raw content.
- Duplicate IDs remain untouched. ID-addressed operations stop with `identity_conflict` until you resolve the files.

## Identity and revisions

Paths describe current locations. A move or rename does not change the frontmatter ID. The content revision is the BLAKE3 hash of the current file bytes. Update, move, and delete operations require the revision observed by the caller.

## Local metadata

`.noura/workspace.yaml` stores the workspace manifest. Deleting a file moves it to the operating system trash. When the system has no trash or refuses the move, the application moves the file to `.noura/trash/<timestamp>/<original-relative-path>` instead. Applications without an operating system trash, such as the browser build, always use that folder. `.noura/history/<object-id>/` stores Markdown snapshots that let you recover versions displaced during external-edit reconciliation. Scanners ignore `.noura`, folders and files whose names start with a dot (such as `.obsidian` or `.DS_Store`), and top-level `node_modules` and `target` folders. They treat an iCloud placeholder such as `.Note.md.icloud` as the file `Note.md` that has not been downloaded yet. SQLite indexes, process locks, provider configuration, recent workspaces, and credentials do not belong in the workspace.

The application also writes these folders under `.noura`:

- `.noura/chat-mutations/`: one JSON intent file per chat change in progress. An intent holds the new bytes for a chat file and one message file. The application writes the intent before it changes those files and deletes it afterward. If an intent remains after a crash, the application writes its files the next time it reads the workspace.
- `.noura/sync/`: local state for encrypted sync, such as `config.json`, the `state.json` journal, validated key envelopes under `keys/`, and encrypted attachment blobs under `blobs/`. Only encrypted sync writes this folder. [Encrypted synchronization](sync-v1.md) defines its contents. The application never uploads it as a workspace file.
- `.noura/browser-storage/`: journals and staged writes for the browser build's workspace storage. Only the browser build writes this folder.

## Chats

Chats are durable managed Markdown. The application stores a newly created chat at `chats/<slug>--<chat-short-id>/chat.md`, where `chat-short-id` is the final six characters of the chat ULID. It stores messages beneath that directory at `messages/YYYY-MM-DD/chat-message_<ulid>.md`. Application writes always use this layout; stable IDs remain the identity if you move a file externally.

```markdown
---
id: chat_01j00000000000000000000000
type: chat
title: Release planning
retention: ephemeral
retention_days: 30
created: 2026-09-02T12:00:00Z
updated: 2026-09-02T12:00:00Z
---
```

Chats use `retention: ephemeral` with `retention_days: 30`, or `retention: permanent` with `retention_days: null`. A permanently retained chat may omit `retention_days`; readers treat the omission as `null` and writers serialize `null`. Local retention cleanup can move an ephemeral chat 30 days after creation. Retention moves only a fully valid, unchanged canonical chat directory to the trash, following the same rules as a deleted file; unknown files, malformed files, symlinks, moved chat directories, and files modified after expiry are retained.

```markdown
---
id: chat-message_01j00000000000000000000000
type: chat-message
chat_id: chat_01j00000000000000000000000
run_id: run_123
kind: tool-call
status: in-progress
content_type: application/json
provider_id: null
model_id: null
tool_call_id: call_123
tool_name: workspace.search
error_code: null
summarizes_through_message_id: null
created: 2026-09-02T12:01:00Z
updated: 2026-09-02T12:01:00Z
---

{"query":"release notes"}
```

Every message has `chat_id`, `run_id`, `kind`, `status`, and `content_type`. `run_id` must be non-empty after trimming and contain no control characters. Kinds are `user`, `assistant`, `tool-call`, `tool-result`, or `context-summary`; statuses are `in-progress`, `completed`, `interrupted`, `cancelled`, or `failed`. Assistant messages require `provider_id` and `model_id`; tool messages require `tool_call_id`, `tool_name`, `content_type: application/json`, and a deterministic JSON body. When present, provider, model, and tool metadata must be non-empty and contain no control characters. Failed messages require `error_code`; interrupted messages may include one. Other statuses omit it. An error code is at most 128 ASCII bytes and uses only letters, digits, dots, hyphens, or underscores. Context summaries require `summarizes_through_message_id`, which identifies a chat message. Fields not applicable to a kind may be `null` or omitted; readers treat omission as `null` and writers serialize `null`.

The application preserves unknown frontmatter properties on read-modify-write. Interrupted assistant messages recover as `interrupted`. An interrupted tool-call recovers as `completed` only when the same chat contains a completed durable tool-result with the same `run_id`, `tool_call_id`, and `tool_name`; otherwise it recovers as `interrupted`. Every append or finish request requires the current chat revision, and message finishes also require the current message revision. SQLite indexes derive the `chat_id` relation and are always rebuildable from these files.
