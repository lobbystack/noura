# Workspace format v1

A Noura workspace is a normal directory with its manifest at `.noura/workspace.yaml`. Markdown files with valid managed frontmatter become workspace objects. Other files remain ordinary files.

## Manifest

Noura keeps its own workspace-level files under `.noura` so the workspace root remains user content.

```yaml
id: workspace_01k...
format_version: 1
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
enabled_plugins:
  - calendar
  - dictation
  - projects
  - tasks
  - transcription
ignore: []
```

The workspace ID identifies the workspace across moves. Device-local indexes and credentials live in operating system application-data and credential directories.

A workspace has no name of its own. Noura shows its folder's name, so renaming the folder renames the workspace. Readers ignore keys the manifest doesn't define, such as the `name` key that earlier versions wrote, and the application drops them the next time it writes the file.

`enabled_plugins` lists the identifiers of the modules the workspace turns on. Rules:

- Plugin identifiers are a lowercase letter followed by lowercase letters, digits, or hyphens, at most 64 characters total.
- Order is not significant, and writers deduplicate the list. Readers tolerate a hand edit's duplicates and unsorted entries by canonicalizing on read; writers serialize the deduplicated list in sorted order.
- An empty list is valid and enables no domain modules.
- Readers preserve unknown identifiers and ignore IDs they do not implement, so future ecosystem plugins do not break older builds.
- Application plugin toggles rewrite this file atomically and refresh `updated`.
- `sync` turns encrypted sync and collaboration on for this replica. New workspaces don’t enable it. A replica created by joining a synchronized workspace enables it.

## Managed Markdown

A task that the Tasks plugin saved as `Tasks/Prepare release notes.md`:

```markdown
---
id: task_01k...
type: task
status: todo
priority: medium
project: '[[Release 0.3]]'
due: 2026-09-04
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
---
Summarize user-visible changes.
```

IDs use a lowercase object-type prefix and lowercase ULID. Timestamps use RFC 3339 UTC. A date property holds `YYYY-MM-DD` for an all-day value, or RFC 3339 with an explicit offset for a timed one.

The format knows no field of any type beyond the envelope. The task above has `status`, `priority`, `project` and `due` because the Tasks plugin declares them, as [Task and project types](#task-and-project-types) shows. With the plugin off, the same file is a generic managed object that keeps every property.

The serializer writes the properties of a registered type in its schema's order and sorts the rest by key. It preserves unknown JSON-compatible values. It does not preserve YAML comments, aliases, tags, or the original formatting of frontmatter that an application mutation changes. [Object types](#object-types) defines the envelope every managed object shares and the order a registered type's schema sets.

## Classification

- A file with valid `id` and `type` fields becomes a managed object.
- Idless Markdown remains unmanaged until explicit adoption.
- Malformed frontmatter remains untouched and searchable as raw content.
- Duplicate IDs remain untouched. ID-addressed operations stop with `identity_conflict` until you resolve the files.

## Object types

Every managed object shares one envelope, whatever its type. A plugin can register its type with a property schema, which adds validation, defaults and a property order. The shared fixture `fixtures/object-envelope-v1.json` covers each rule in this section.

### Envelope

A managed Markdown file holds these parts:

- **`id`:** the type, an underscore and a lowercase ULID, as in `recipe_01j00000000000000000000000`.
- **`type`:** a lowercase letter followed by lowercase letters or hyphens. It must match the ID's prefix.
- **`created` and `updated`:** RFC 3339 instants. Parsers read them only when they're strings and drop any other value.
- **Properties:** every other frontmatter key, with any JSON-compatible value.
- **Title:** the file's name without its extension. `Notes/Team sync.md` holds the note titled `Team sync`, so renaming the file renames the object. A heading in the file is ordinary body text, and Noura never writes or rewrites one. Chats keep their own `title` property, as [Chats](#chats) describes.
- **Body:** the text after the closing `---` line, as written.

The frontmatter ends at the next line that holds only `---` and ends with a line break. The line break before that line belongs to the YAML, so a multi-line value written last keeps its final line break. Parsers skip a byte-order mark at the start of the file and read CRLF as LF. In the body, they also read a run of carriage returns right before a line feed as one line break.

The serializer writes the frontmatter and then the body as it gets it. It adds no heading and no blank line, and it adds or drops no line break at the end, so a body without a final line break makes a file without one.

Serializing a parsed object gives canonical bytes. Parse canonical bytes and serialize the object again, and you get the same bytes. A body you pass straight to the serializer can change once more: the next read turns its CRLF line breaks into LF.

YAML 1.1 readers such as libyaml treat U+0085, U+2028 and U+2029 as line breaks. YAML 1.2 readers treat them as ordinary characters. The serializer writes keys and values the way libyaml does: it double-quotes a string that holds U+0085, escaped as `\N`, and writes U+2028 and U+2029 raw in single-quoted strings and literal blocks. libyaml reads all of these back unchanged, but a YAML 1.2 reader can get different text.

The serializer departs from libyaml in one case. libyaml can write a string that holds a line feed as a literal block. When the frontmatter's last value is a literal block that ends in U+2028 or U+2029, libyaml's output has no final line feed. The closing `---` would then share that line, and the file would read back as malformed. The serializer writes that last value in double quotes instead, with the escapes `\L` and `\P`:

```yaml
steps: "Boil.\nServe.\L"
```

If another entry follows, the literal block stays as libyaml writes it. The raw separator ends the block's last line, and the next key starts right after it.

### Saving over a file

An application that changes an existing file writes only what changed. When the properties stay the same, the frontmatter keeps its bytes, comments and odd spacing included. When the body stays the same, it keeps its bytes. The file keeps its byte-order mark, its final line break or the lack of one, and the ending of each line you didn't change. A line you edit keeps its own ending. A new line takes the ending most of the file's lines use, or LF on a tie. The `rewrites` section of `fixtures/conformance-v1.json` shows each rule. When the properties of a registered type change, the new frontmatter takes that type's [canonical order](#canonical-order), as the `registered_rewrites` section of `fixtures/object-envelope-v1.json` shows.

### Names

A new object gets a file named after its title, in a folder named after its type in the plural, starting with a capital letter: `Notes/<title>.md` for a note, `Tasks/<title>.md` for a task and `Recipes/<title>.md` for a recipe. A plugin can pass its own path instead. The Projects plugin gives each project a folder of its own, as `Projects/<title>/<title>.md`, so the folder can hold the project's notes and files. When the name is taken, the application or the plugin adds a number, as in `Meeting 1.md` or `Projects/Garden 1/Garden 1.md`. The `default_paths` section of `fixtures/conformance-v1.json` lists examples.

When a folder on the path already exists with a name that differs only in letter case, such as `notes/` made by an older version or another app, the application writes into that folder and records its spelling, so a case-insensitive disk never holds two names for one folder. Objects in a lowercase folder stay where they are, and the application finds them by ID.

Before an application uses a typed title as a file name, it removes path separators, control characters and the characters macOS or Windows reject (`\ / : * ? " < > |`). It then drops leading dots, which would hide the file, and the spaces around the name, and keeps the first 200 characters. It drops trailing dots too, because Windows removes them from file names. When nothing is left, the old name stays.

Windows reserves `CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9` and `LPT1` to `LPT9` for devices, in any letter case and even before a dot. The application adds an underscore after such a name, so `CON` becomes `CON_`. The `titles` and `file_names` sections of `fixtures/conformance-v1.json` cover these rules.

### Schema declaration

A schema lists a type's properties in the order you want them written:

```json
{
  "properties": [
    { "name": "status", "kind": { "enum": ["todo", "done"] }, "default": "todo" },
    { "name": "project", "kind": { "reference": "project" }, "nullable": true },
    { "name": "due", "kind": "date", "nullable": true }
  ]
}
```

Each declaration has a `name` and a `kind`. Add `"nullable": true` to accept `null`, and `default` to give a value for a missing property. A schema or declaration with any other key fails to decode. The `kind` takes one of these values:

| Kind | Accepts |
|---|---|
| `"string"` | Any string |
| `"number"` | Any number |
| `"boolean"` | `true` or `false` |
| `"date"` | A civil date (`YYYY-MM-DD`) or an RFC 3339 instant with `Z` or an explicit offset |
| `{ "enum": [...] }` | One of the listed strings |
| `{ "reference": "object_type" }` | A [link](#links), such as `"[[Garden]]"`, to an object of the named type, or of any type with `"*"` |
| `{ "id": "object_type" }` | The stable ID of an object of the named type, for an object that belongs to another, as a chat message to its chat |
| `{ "list": kind }` | A list of values of one kind, such as `{ "list": { "reference": "*" } }` for several links. A list of lists is invalid. |

A default must fit its own declaration, so `"default": null` needs `"nullable": true`.

Validation checks a reference's form. When an application writes an object of a registered type, it also checks that each link it sets leads to an object of the named type, and refuses the write with `invalid_reference` otherwise. A plain note without an ID isn't an object, so a reference can't lead to one.

Noura uses this declaration instead of JSON Schema. JSON Schema keeps properties in an unordered object, so it can't set a write order or catch a property declared twice. Its validators don't apply defaults, and it has no keyword for a link or a stable ID.

### Registration

Registering a type fails with one of these structured errors:

| `code` | Names | When |
|---|---|---|
| `invalid_type_name` | `object_type` | The type name breaks the rule for `type` above. |
| `reserved_property` | `property` | The schema declares `id`, `type`, `created` or `updated`. |
| `duplicate_property` | `property` | Two declarations share a name. |
| `invalid_declaration` | `property` | The name is empty, an enum lists no values, a reference or an ID names an invalid type, or a list holds lists. |
| `invalid_default` | `property` | The default doesn't fit its declaration. |
| `type_already_registered` | `object_type` | Another schema already holds the type. |

### Validation

Validation checks each declared property an object holds and adds the default of each declared property it lacks. Unknown properties stay as written. The first property that fails, in declared order, stops validation and leaves the object unchanged. The error names the property in `property` and gives one of these codes:

| `code` | When |
|---|---|
| `wrong_type` | The value has the wrong JSON type, or is `null` on a property that isn't nullable. |
| `not_allowed` | An enum value isn't in the list. |
| `invalid_date` | A date string is neither a civil date nor an instant with an offset. |
| `invalid_reference` | A reference isn't a link, or an `id` isn't the stable ID of an object of the named type. |

A file whose properties fail its schema still parses as a managed object. Applications report the failing property against the plugin that declares the schema, and leave the file's bytes alone.

A declared kind also checks the value's JSON type, so a task file with `due: 5` fails the Tasks plugin's `date` declaration with `wrong_type`.

### Canonical order

The serializer writes a registered type's frontmatter in this order:

1. `id`, then `type`.
2. The declared properties the object holds, in declared order.
3. Every other property, sorted by key.
4. `created`, then `updated`.

A type without a registered schema has nothing in step 2, so every property sorts by key. Notes work this way, and so do tasks and projects while their plugins are off. Chats and chat messages keep the layout in [Chats](#chats).

Serialization writes values as they are. It doesn't validate them or add defaults. A mapping inside a value sorts by key at every depth, so the bytes depend only on the values.

### Unregistered types

A file whose type has no registered schema parses as a generic managed object. Validation leaves it unchanged, and the serializer writes every property as written, sorted by key. A missing schema never makes a file malformed, so turning a plugin off can't break the plugin's files. Saving over a file still keeps the bytes of every part you didn't change, as [Saving over a file](#saving-over-a-file) describes.

### Task and project types

The Tasks and Projects plugins ship with Noura and register the `task` and `project` types. The Tasks plugin declares this schema for a task:

```json
{
  "properties": [
    { "name": "status", "kind": { "enum": ["todo", "in-progress", "done", "cancelled"] }, "default": "todo" },
    { "name": "priority", "kind": { "enum": ["low", "medium", "high", "urgent"] }, "default": "medium" },
    { "name": "project", "kind": { "reference": "project" }, "nullable": true },
    { "name": "source", "kind": { "reference": "*" }, "nullable": true },
    { "name": "due", "kind": "date", "nullable": true },
    { "name": "kanban_order", "kind": "string" }
  ]
}
```

A task's `project` links to its project. Its `source` links to the object the task came from, such as the Transcription whose action items it holds.

The Projects plugin declares this schema for a project:

```json
{
  "properties": [
    {
      "name": "status",
      "kind": { "enum": ["planned", "active", "on-hold", "completed", "cancelled"] },
      "default": "planned"
    }
  ]
}
```

Each plugin's fixture lists the values its type accepts and refuses, and the order its files take: `crates/plugins/tasks/fixtures/task-v1.json` and `crates/plugins/projects/fixtures/project-v1.json`.

### Transcription types

The Transcription plugin ships with Noura. It registers three types: `transcription`, `transcript` and `transcription-settings`. A Transcription is a folder, `Meetings/<title>/` or a folder inside the chosen project's folder, that holds two files. `<title>.md` is the `transcription`, with your notes and the Summary. `Transcript.md` is its `transcript`. The plugin declares this schema for a Transcription:

```json
{
  "properties": [
    { "name": "start", "kind": "date", "nullable": true },
    { "name": "end", "kind": "date", "nullable": true },
    { "name": "project", "kind": { "reference": "project" }, "nullable": true },
    { "name": "attendees", "kind": { "list": "string" }, "default": [] }
  ]
}
```

`start` and `end` hold the times the recording started and stopped, so Calendar shows the Transcription. `project` links to its project, and `attendees` lists who took part by name.

The body holds your notes, then a `## Summary` section that the plugin writes. The section runs to the next heading of level 1 or 2, or to the end of the file. Summarizing again replaces only that section and leaves the bytes before it as they were. The plugin moves the Summary's own headings two levels deeper, so `# Next Steps` becomes `### Next Steps`.

A Transcript links back to its Transcription:

```json
{
  "properties": [
    { "name": "transcription", "kind": { "reference": "transcription" }, "nullable": true }
  ]
}
```

Its body holds one paragraph per speaker turn. The paragraph's first line names the speaker and the time from the start of the recording, then the next line holds what they said:

```markdown
**Me** · 00:03:12
Let's ship on Friday.

**Others** · 00:03:15
I'll write the release notes.
```

`Me` is the microphone and `Others` is the sound other apps played. You can edit the Transcript. The next Summary reads it as you left it.

The plugin's settings live in one `transcription-settings` file, which Noura creates as `Meetings/Transcription settings.md`:

```json
{
  "properties": [
    { "name": "folder", "kind": { "enum": ["project", "meetings"] }, "default": "project" },
    { "name": "provider", "kind": "string", "nullable": true },
    { "name": "language", "kind": "string", "nullable": true },
    { "name": "audio", "kind": { "enum": ["none", "folder", "device"] }, "default": "none" },
    { "name": "audio_days", "kind": "number", "default": 30 }
  ]
}
```

`folder` puts a new Transcription in its project's folder, or always in `Meetings/`. `provider` holds the ID of the AI provider that writes the Summary, or `null` for your first. `language` holds the Summary's language as an ISO 639-1 code, or `null` for the language that Settings, Speech holds.

`audio` drops the recording, saves it as a WAV file in the Transcription's folder, or keeps it in this device's app data folder for `audio_days` days. The body holds the Summary's prompt, which replaces the default format instructions. An empty body keeps the default.

The plugin's fixture, `crates/plugins/transcription/fixtures/transcription-v1.json`, lists the values each type accepts and refuses, and the order its files take.

The Calendar plugin shows any object's `due`, `date` and `start` properties, with its `end`, as calendar entries. It registers no type, so these stay ordinary properties of whatever type holds them. Its fixture, `crates/plugins/calendar/fixtures/calendar-v1.json`, holds the entries it finds in the files of `fixtures/queries-v1.json`.

### Malformed files

These files are malformed whether or not a plugin registered their type:

- Bytes that aren't UTF-8.
- Invalid YAML in the frontmatter.
- A frontmatter block with no closing `---` line.
- An `id` without a string `type`.
- An ID that doesn't match its type.

## Links

A link points from one file to another by the other file's title: `[[Garden]]`. When two files share the title, a link names the file by its path from the top of the workspace, without `.md`: `[[Projects/Garden/Garden]]`. A link may add a heading after `#` or a label after `|`, as in `[[Garden#Beds|the beds]]`, and `![[Garden]]` embeds the file. Links work the same in a body and in a property, where the whole value is the link, as in `project: '[[Garden]]'`. A list property holds one link per item.

A link leads to the first file that matches, in this order:

1. The path relative to the linking file's folder, then from the top of the workspace, each tried with `.md` added first unless the target names an extension.
2. Any file with that name, ignoring case. The linking file's folder comes first, then the shortest path, then the path in alphabetical order without case.

Links inside fenced code blocks and inline code are text, not links.

When a file moves or gets a new title, inside Noura or in another app, the application rewrites every link that led to it, so each still leads there. It finds a moved object by its stable ID, so a rename in a file manager or with Git counts too. It writes `[[Title]]` when that still leads to the file, and the path otherwise, and changes only the bytes of each link's target. A link that still leads to the moved file stays as it is. Before it writes, the application checks that the file still holds what it read. When the file changed meanwhile, or when the new title can't stand in the property as it is written, as a title with `'` in a single-quoted value of a file without an ID, the application leaves the file alone and lists it among the workspace's problems.

Backlinks, the files that link to a file, come from the index. No file stores them, so a rebuilt index finds the same ones.

The `links` section of `fixtures/conformance-v1.json` covers these rules.

## Identity and revisions

Paths describe current locations. A move or rename does not change the frontmatter ID. The content revision is the BLAKE3 hash of the current file bytes. Update, move, and delete operations require the revision observed by the caller.

## Local metadata

`.noura/workspace.yaml` stores the workspace manifest. Deleting a file moves it to the operating system trash. When the system has no trash or refuses the move, the application moves the file to `.noura/trash/<timestamp>/<original-relative-path>` instead. Applications without an operating system trash, such as the browser build, always use that folder. `.noura/history/<object-id>/` stores Markdown snapshots that let you recover versions displaced during external-edit reconciliation. The editor keeps its snapshots of notes, plain-text files and code files in `.noura/history/raw-<digest>/`. The digest is the first 16 hex digits of the BLAKE3 hash of the file's workspace-relative path. Each name is `<revision>-external.md` for a file version the editor replaced, or `<revision>-local.md` for a version of yours. Scanners ignore `.noura`, folders and files whose names start with a dot (such as `.obsidian` or `.DS_Store`), and top-level `node_modules` and `target` folders. They treat an iCloud placeholder such as `.Note.md.icloud` as the file `Note.md` that has not been downloaded yet. A `.noura-domain` file is the one exception sync makes to the dot-file rule: scanners still leave it out of the workspace's objects, but encrypted sync reads it and writes it as the marker of a restricted folder, with the content `domain: <base64url domain ID>` and a line feed, as [sync protocol version 2](sync-v2.md#domain-roots) defines. An iCloud placeholder of the marker, `.noura-domain.icloud` or `..noura-domain.icloud`, counts as the marker, and a scanner doesn't read it as a file named `noura-domain`. SQLite indexes, process locks, provider configuration, recent workspaces, and credentials do not belong in the workspace.

The application also writes these folders under `.noura`:

- `.noura/chat-mutations/`: one JSON intent file per chat change in progress. An intent holds the new bytes for a chat file and one message file. The application writes the intent before it changes those files and deletes it afterward. If a file changes while the application commits, the application puts the message file back, deletes the intent and reports `revision_conflict`. If an intent remains after a crash, the application writes its files the next time it reads the workspace. Your edits win over the intent. If you edited the chat file, the application keeps your bytes and still writes the message, because the intent changes only `updated` in the chat file. If you edited the message file or moved the chat, the application writes neither file. It renames the intent to `<id>.unapplied`, which holds the bytes it didn't write. The application never reads that file again, so you can delete it. When the application can't read an intent, it leaves the intent and both files as they are and tries again on each read. Until then that chat stops with `chat_mutation_recovery_invalid` when you open or change it, and the rest of the workspace keeps working. Delete the intent to reopen the chat. While a disk refuses the write or a file waits to download, the chat reads as its files stand and refuses changes. An intent that names no chat stops nothing and stays in the folder.
- `.noura/sync/`: local state for encrypted sync, such as `config.json`, the `state.json` journal, validated key envelopes under `keys/`, and encrypted attachment blobs under `blobs/`. `plugin.json` records that this replica's `sync` plugin state was set once, so the application never turns the plugin back on after you turn it off. Only encrypted sync writes this folder. [Encrypted synchronization](sync-v1.md) defines its contents. The Rust product's [sync protocol version 2](sync-v2.md#client-journal) keeps one journal per device under `.noura/sync/<device-id>/` instead. The application never uploads it as a workspace file.
- `.noura/browser-storage/`: journals and staged writes for the browser build's workspace storage. Only the browser build writes this folder.

## Chats

Chats are durable managed Markdown. The application stores a newly created chat at `Chats/<slug>--<chat-short-id>/chat.md`, where `chat-short-id` is the final six characters of the chat ULID. It stores messages beneath that directory at `messages/YYYY-MM-DD/chat-message_<ulid>.md`. Application writes always use this layout; stable IDs remain the identity if you move a file externally.

```markdown
---
id: chat_01j00000000000000000000000
type: chat
title: Release planning
retention: ephemeral
retention_days: 30
created: 2026-09-02T12:00:00Z
updated: 2026-09-02T12:00:00Z
---
```

A chat that is an [Orb](#orbs)'s thread holds `orb_id`, the Orb's stable ID, after `title`. A chat without `orb_id`, or with `orb_id: null`, belongs to the default Orb, so chats from before Orbs need no change. Writers omit `orb_id` for a chat without an Orb, and a value that isn't an Orb's stable ID makes the chat invalid.

Chats use `retention: ephemeral` with `retention_days: 30`, or `retention: permanent` with `retention_days: null`. A permanently retained chat may omit `retention_days`; readers treat the omission as `null` and writers serialize `null`. Local retention cleanup can move an ephemeral chat 30 days after creation. Retention moves only a fully valid, unchanged canonical chat directory to the trash, following the same rules as a deleted file; unknown files, malformed files, symlinks, moved chat directories, and files modified after expiry are retained.

```markdown
---
id: chat-message_01j00000000000000000000000
type: chat-message
chat_id: chat_01j00000000000000000000000
run_id: run_123
kind: tool-call
status: in-progress
content_type: application/json
provider_id: null
model_id: null
tool_call_id: call_123
tool_name: workspace.search
error_code: null
summarizes_through_message_id: null
created: 2026-09-02T12:01:00Z
updated: 2026-09-02T12:01:00Z
---

{"query":"release notes"}
```

Every message has `chat_id`, `run_id`, `kind`, `status`, and `content_type`. `run_id` must be non-empty after trimming and contain no control characters. Kinds are `user`, `assistant`, `tool-call`, `tool-result`, or `context-summary`; statuses are `in-progress`, `completed`, `interrupted`, `cancelled`, or `failed`. Assistant messages require `provider_id` and `model_id`; tool messages require `tool_call_id`, `tool_name`, `content_type: application/json`, and a deterministic JSON body. When present, provider, model, and tool metadata must be non-empty and contain no control characters. Failed messages require `error_code`; interrupted messages may include one. Other statuses omit it. An error code is at most 128 ASCII bytes and uses only letters, digits, dots, hyphens, or underscores. Context summaries require `summarizes_through_message_id`, which identifies a chat message. Fields not applicable to a kind may be `null` or omitted; readers treat omission as `null` and writers serialize `null`.

The application preserves unknown frontmatter properties on read-modify-write. Interrupted assistant messages recover as `interrupted`. An interrupted tool-call recovers as `completed` only when the same chat contains a completed durable tool-result with the same `run_id`, `tool_call_id`, and `tool_name`; otherwise it recovers as `interrupted`. Every append or finish request requires the current chat revision, and message finishes also require the current message revision. SQLite indexes derive the `chat_id` relation and are always rebuildable from these files.

Noura reads a chat file through the managed-object [envelope](#envelope) and writes its frontmatter with the envelope's YAML. A title that ends in U+2028 reads back as written. The AI plugin registers the `chat` and `chat-message` types with the schemas in the `schemas` section of `fixtures/object-envelope-v1.json`, and each schema states a field's kind.

Noura writes chat files only through its AI service, which places each file in the chat layout and checks the rules above, such as an assistant message's provider and model. A plugin reads chats through the objects interface, but Noura refuses a create, update, move or delete of a chat or message there, even from the AI plugin. When Noura lists chats or reads one for the AI page, it checks the same rules. A chat or message file that breaks them, as after an edit in another app, keeps its bytes and stays out of the chat list or the chat.

## Orbs

An Orb is a personal agent that lives in the workspace: a name, instructions you write, the tools it runs without asking, what it remembers, and triggers that start it while you're away. The AI plugin registers the `orb` and `orb-run` types with the schemas in `fixtures/orb-v1.json`, and that fixture covers every rule in this section.

### Orb folder

Noura creates each Orb in a folder of its own under `Orbs/`, named after the Orb:

```text
Orbs/
  Meetings/
    Meetings.md                  the Orb (type: orb); its title is the file name
    Memory.md                    what it remembers, a note
    Heartbeat.md                 the checklist its scheduled runs follow, a note
    Runs/
      2026-11-21/
        orb-run_01jd8x….md       one record per run
```

The layout follows OpenClaw's agent workspace, adapted to Noura's objects: `<title>.md` holds the instructions, as OpenClaw's `AGENTS.md` and `SOUL.md` do, its frontmatter holds the identity that OpenClaw keeps in `IDENTITY.md`, `Memory.md` plays the part of `MEMORY.md`, and `Heartbeat.md` that of `HEARTBEAT.md`. The stable ID names the Orb, so you can rename or move its folder. Noura finds the files beside it from the Orb file's folder, and `memory` follows a link.

### Orb type

```markdown
---
id: orb_01jd8x3k9q2m7v4c6b1n0p5r8t
type: orb
avatar: 🗓
color: blue
provider: null
model: null
tools:
- tasks__create
- tasks__list
reads:
- '[[Acme launch]]'
memory: '[[Memory]]'
triggers:
- event transcription.finished
- schedule 30 8 * * 1-5
paused: false
created: 2026-11-21T12:00:00Z
updated: 2026-11-21T12:00:00Z
---
You turn meetings into follow-ups. When a Transcription ends, create a task for each commitment someone made.
```

The title is the Orb's name and the body holds its instructions. The properties, in canonical order:

| Property | Holds |
|---|---|
| `avatar` | An emoji or up to 16 characters, or `null` |
| `color` | One of `red`, `orange`, `yellow`, `green`, `blue`, `purple`, `brown` or `gray`, or `null` |
| `provider` | The ID of an AI provider on this device, or `null` for your first. Provider IDs belong to each device, so another device that lacks this one uses its first provider. |
| `model` | A model in place of the provider's own, or `null` |
| `tools` | The tools the Orb runs without asking, each named as the model sees it: `<plugin>__<tool>`, or `<plugin>__*` for every tool of a plugin. Noura's own tools are the `noura` plugin's: `noura__read`, `noura__remember`, `noura__web_search` and `noura__web_fetch`. A tool appears at most once. |
| `reads` | Links to the objects its read tool and its trigger messages may open. An empty list means the whole workspace. |
| `memory` | A link to its memory file, or `null` for none |
| `triggers` | What starts it without you, as described in [Triggers](#triggers). A trigger appears at most once. |
| `paused` | `true` when you paused it: no trigger fires |

An Orb whose properties break these rules stays as you wrote it, and Noura neither runs it nor fires its triggers until you fix the file. Reading it reports the first failing property in declared order, with a schema code from [Validation](#validation) or one of `invalid_avatar`, `invalid_provider`, `invalid_model`, `invalid_tool`, `duplicate_tool`, `invalid_trigger`, `schedule_too_frequent` or `duplicate_trigger`.

Plugins read Orbs through the objects interface, and Noura refuses their creates, updates, moves and deletes there, as it does for chats, so no model tool can grant an Orb more tools or triggers. You change an Orb by editing its file, and the AI plugin changes it through the `ai` interface.

### Memory and heartbeat

`Memory.md` is a note, with an ID so that `memory` can link to it. Noura sends its body with every request of the Orb's, after the instructions. The `noura__remember` tool adds a line to its end, and you can edit or delete anything in it.

`Heartbeat.md` is a note whose body a schedule trigger sends as its message. Without it, or with an empty body, a scheduled run sends the time it fired for. An Orb that finds nothing to do answers `HEARTBEAT_OK`, as OpenClaw's heartbeat does. Noura records that run as quiet and shows no notification for it.

### Triggers

Each trigger is one string, a keyword, a space and its argument:

- **`schedule <pattern>`**: the times a 5-field cron pattern names, in this device's time zone, such as `schedule 30 8 * * 1-5` for weekday mornings at 8:30. Patterns follow croner, which accepts names such as `MON` and `JAN` and the nicknames `@hourly`, `@daily`, `@weekly`, `@monthly` and `@yearly`. Times come at least 5 minutes apart, and a pattern that fires more often fails with `schedule_too_frequent`. A time that a daylight saving change skips runs at the next minute that exists.
- **`event <plugin>.<event>`**: an event a plugin declares and tells Noura about, such as `event transcription.finished` when a Transcription ends. Both parts use a plugin ID's characters.

Noura writes a trigger with single spaces, and compares triggers in that form. A trigger in any other form, or one written as a YAML mapping, makes the Orb invalid.

Triggers fire only while Noura is open on one of your devices. At launch, each schedule trigger catches up once on the last time it missed since its previous run, or since the Orb's file was created. A trigger key names each firing: the Orb's ID, the trigger and the occurrence, joined by `|`. The occurrence is the scheduled time in UTC, or the object an event names, `@`, and the first 16 hex digits of that object's revision. Noura starts no run for a key that a run record already holds.

### Run records

Each run, whether you or a trigger started it, leaves an `orb-run` record at `Runs/<YYYY-MM-DD>/<id>.md` beside the Orb, named after its stable ID:

```markdown
---
id: orb-run_01jd8x3k9q2m7v4c6b1n0p5r8b
type: orb-run
orb_id: orb_01jd8x3k9q2m7v4c6b1n0p5r8t
chat_id: chat_01jd8x3k9q2m7v4c6b1n0p5r8c
started_by: event
trigger: event transcription.finished
trigger_key: orb_01jd8x3k9q2m7v4c6b1n0p5r8t|event transcription.finished|transcription_01jd8x3k9q2m7v4c6b1n0p5r8a@9f86d081884c7d65
object_id: transcription_01jd8x3k9q2m7v4c6b1n0p5r8a
slot: null
status: succeeded
error_code: null
tool_calls: 2
quiet: false
resumed: 0
finished: 2026-11-21T12:01:00Z
created: 2026-11-21T12:00:00Z
updated: 2026-11-21T12:01:00Z
---
- `tasks__create` · completed
- `tasks__create` · completed
```

`started_by` is `you`, `schedule` or `event`. `status` is `running`, `succeeded`, `failed`, `interrupted` or `cancelled`. `created` holds when the run started, `finished` when it ended, and `error_code` why a failed or interrupted run stopped. The body lists each tool call the run made, one line each. The run's messages live in the Orb's thread, the chat whose `orb_id` names the Orb, under the run's ID as their `run_id`.

Noura writes the record before the run's first message, and again when the run ends. A record left `running` after Noura quit is one Noura takes up at the next launch: when no tool call of the run waits without its result, Noura asks the provider to answer again, once, and adds one to `resumed`. A run that quit during a tool call, or that Noura already took up once, becomes `interrupted` with `error_code: orb_interrupted`, because Noura never runs a tool call again by itself.

### Default Orb

The default Orb has the stable ID `orb_00000000000000000000000000` and no file. Plain chats belong to it: every chat without `orb_id`. It uses Noura's instructions and the workspace's `AGENTS.md`, offers every tool of the plugins on in the workspace, and asks before each tool call runs.
