# Workspace format v1

A Noura workspace is a normal directory with its manifest at `.noura/workspace.yaml`. Markdown files with valid managed frontmatter become workspace objects. Other files remain ordinary files.

## Manifest

Noura keeps its own workspace-level files under `.noura` so the workspace root remains user content.

```yaml
id: workspace_01k...
format_version: 1
name: Example workspace
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
enabled_plugins:
  - folders
  - notes
  - tasks
  - calendar
  - projects
ignore: []
```

The workspace ID identifies the workspace across moves. Device-local indexes and credentials live in operating system application-data and credential directories.

`enabled_plugins` lists the identifiers of the modules the workspace turns on. Rules:

- Plugin identifiers are a lowercase letter followed by lowercase letters, digits, or hyphens, at most 64 characters total.
- Order is not significant, and writers deduplicate the list. Readers tolerate a hand edit's duplicates and unsorted entries by canonicalizing on read; writers serialize the deduplicated list in sorted order.
- An empty list is valid and enables no domain modules.
- Readers preserve unknown identifiers and ignore IDs they do not implement, so future ecosystem plugins do not break older builds.
- Application plugin toggles rewrite this file atomically and refresh `updated`.
- `sync` turns encrypted sync and collaboration on for this replica. New workspaces don’t enable it. A replica created by joining a synchronized workspace enables it.

## Managed Markdown

A task saved as `tasks/Prepare release notes.md`:

```markdown
---
id: task_01k...
type: task
status: todo
priority: medium
project: null
due: 2026-09-04
created: 2026-08-27T18:00:00Z
updated: 2026-08-27T18:00:00Z
---
Summarize user-visible changes.
```

IDs use a lowercase object-type prefix and lowercase ULID. Timestamps use RFC 3339 UTC. The serializer accepts `YYYY-MM-DD` for all-day date properties or RFC 3339 with an explicit offset for timed values.

The serializer writes known fields in canonical order and sorts unknown properties by key. It preserves unknown JSON-compatible values. It does not preserve YAML comments, aliases, tags, or the original formatting of frontmatter that an application mutation changes. [Object types](#object-types) defines the envelope every managed object shares and the order a registered type's schema sets.

## Classification

- A file with valid `id` and `type` fields becomes a managed object.
- Idless Markdown remains unmanaged until explicit adoption.
- Malformed frontmatter remains untouched and searchable as raw content.
- Duplicate IDs remain untouched. ID-addressed operations stop with `identity_conflict` until you resolve the files.

## Object types

Every managed object shares one envelope, whatever its type. A plugin can register its type with a property schema, which adds validation, defaults and a property order. The shared fixture `fixtures/object-envelope-v1.json` covers each rule in this section.

### Envelope

A managed Markdown file holds these parts:

- **`id`:** the type, an underscore and a lowercase ULID, as in `recipe_01j00000000000000000000000`.
- **`type`:** a lowercase letter followed by lowercase letters or hyphens. It must match the ID's prefix.
- **`created` and `updated`:** RFC 3339 instants. Parsers read them only when they're strings and drop any other value.
- **Properties:** every other frontmatter key, with any JSON-compatible value.
- **Title:** the file's name without its extension. `notes/Team sync.md` holds the note titled `Team sync`, so renaming the file renames the object. A heading in the file is ordinary body text, and Noura never writes or rewrites one. Chats keep their own `title` property, as [Chats](#chats) describes.
- **Body:** the text after the closing `---` line, as written.

The frontmatter ends at the next line that holds only `---` and ends with a line break. The line break before that line belongs to the YAML, so a multi-line value written last keeps its final line break. Parsers skip a byte-order mark at the start of the file and read CRLF as LF. In the body, they also read a run of carriage returns right before a line feed as one line break.

The serializer writes the frontmatter and then the body as it gets it. It adds no heading and no blank line, and it adds or drops no line break at the end, so a body without a final line break makes a file without one.

Serializing a parsed object gives canonical bytes. Parse canonical bytes and serialize the object again, and you get the same bytes. A body you pass straight to the serializer can change once more: the next read turns its CRLF line breaks into LF.

YAML 1.1 readers such as libyaml treat U+0085, U+2028 and U+2029 as line breaks. YAML 1.2 readers treat them as ordinary characters. The serializer writes keys and values the way libyaml does: it double-quotes a string that holds U+0085, escaped as `\N`, and writes U+2028 and U+2029 raw in single-quoted strings and literal blocks. libyaml reads all of these back unchanged, but a YAML 1.2 reader can get different text.

The serializer departs from libyaml in one case. libyaml can write a string that holds a line feed as a literal block. When the frontmatter's last value is a literal block that ends in U+2028 or U+2029, libyaml's output has no final line feed. The closing `---` would then share that line, and the file would read back as malformed. The serializer writes that last value in double quotes instead, with the escapes `\L` and `\P`:

```yaml
steps: "Boil.\nServe.\L"
```

If another entry follows, the literal block stays as libyaml writes it. The raw separator ends the block's last line, and the next key starts right after it.

### Saving over a file

An application that changes an existing file writes only what changed. When the properties stay the same, the frontmatter keeps its bytes, comments and odd spacing included. When the body stays the same, it keeps its bytes. The file keeps its byte-order mark, its final line break or the lack of one, and the ending of each line you didn't change. A line you edit keeps its own ending. A new line takes the ending most of the file's lines use, or LF on a tie. The `rewrites` section of `fixtures/conformance-v1.json` shows each rule.

### Names

A new object gets a file named after its title: `notes/<title>.md` for a note, `tasks/<title>.md` for a task, and `projects/<title>/<title>.md` for a project, whose folder can hold related files. When that name is taken, the application adds a number, as in `Meeting 1.md`.

Before an application uses a typed title as a file name, it removes path separators, control characters and the characters macOS or Windows reject (`\ / : * ? " < > |`). It then drops leading dots, which would hide the file, and the spaces around the name, and keeps the first 200 characters. It drops trailing dots too, because Windows removes them from file names. When nothing is left, the old name stays.

Windows reserves `CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9` and `LPT1` to `LPT9` for devices, in any letter case and even before a dot. The application adds an underscore after such a name, so `CON` becomes `CON_`. The `titles` and `file_names` sections of `fixtures/conformance-v1.json` cover these rules.

### Schema declaration

A schema lists a type's properties in the order you want them written:

```json
{
  "properties": [
    { "name": "status", "kind": { "enum": ["todo", "done"] }, "default": "todo" },
    { "name": "project", "kind": { "reference": "project" }, "nullable": true },
    { "name": "due", "kind": "date", "nullable": true }
  ]
}
```

Each declaration has a `name` and a `kind`. Add `"nullable": true` to accept `null`, and `default` to give a value for a missing property. A schema or declaration with any other key fails to decode. The `kind` takes one of these values:

| Kind | Accepts |
|---|---|
| `"string"` | Any string |
| `"number"` | Any number |
| `"boolean"` | `true` or `false` |
| `"date"` | A civil date (`YYYY-MM-DD`) or an RFC 3339 instant with `Z` or an explicit offset |
| `{ "enum": [...] }` | One of the listed strings |
| `{ "reference": "object_type" }` | The stable ID of an object of the named type |

A default must fit its own declaration, so `"default": null` needs `"nullable": true`.

Noura uses this declaration instead of JSON Schema. JSON Schema keeps properties in an unordered object, so it can't set a write order or catch a property declared twice. Its validators don't apply defaults, and it has no keyword for a stable ID.

### Registration

Registering a type fails with one of these structured errors:

| `code` | Names | When |
|---|---|---|
| `invalid_type_name` | `object_type` | The type name breaks the rule for `type` above. |
| `reserved_property` | `property` | The schema declares `id`, `type`, `created` or `updated`. |
| `duplicate_property` | `property` | Two declarations share a name. |
| `invalid_declaration` | `property` | The name is empty, an enum lists no values, or a reference names an invalid type. |
| `invalid_default` | `property` | The default doesn't fit its declaration. |
| `type_already_registered` | `object_type` | Another schema already holds the type. |

### Validation

Validation checks each declared property an object holds and adds the default of each declared property it lacks. Unknown properties stay as written. The first property that fails, in declared order, stops validation and leaves the object unchanged. The error names the property in `property` and gives one of these codes:

| `code` | When |
|---|---|
| `wrong_type` | The value has the wrong JSON type, or is `null` on a property that isn't nullable. |
| `not_allowed` | An enum value isn't in the list. |
| `invalid_date` | A date string is neither a civil date nor an instant with an offset. |
| `invalid_reference` | A reference isn't the stable ID of an object of the named type. |

A file whose properties fail its schema still parses as a managed object. Applications report the failing property and leave the file's bytes alone.

A declared kind also checks the value's JSON type. Noura's built-in task rules, which apply until the Tasks plugin declares its type, are looser: they check `due` and `project` only when the value is a string, and they don't check `kanban_order`. A task file with `due: 5` passes them but fails a `date` declaration with `wrong_type`. The fixture's `task_schema_differences` section lists each such case.

### Canonical order

The serializer writes a registered type's frontmatter in this order:

1. `id`, then `type`.
2. The declared properties the object holds, in declared order.
3. Every other property, sorted by key.
4. `created`, then `updated`.

A type without a registered schema gets the built-in order instead: the keys `status`, `priority`, `project`, `due`, `date`, `start`, `end` and `kanban_order` take the place of step 2, in that order, and every other property follows, sorted by key. Noura writes notes, tasks and projects this way until the Tasks, Projects and Calendar plugins declare their types. A registered schema replaces the built-in order for its type, so a built-in key that the schema doesn't declare sorts with the other properties. Chats and chat messages keep the layout in [Chats](#chats).

Serialization writes values as they are. It doesn't validate them or add defaults.

### Unregistered types

A file whose type has no registered schema parses as a generic managed object. Validation leaves it unchanged, and the serializer writes every property as written, in the built-in order from [Canonical order](#canonical-order). A missing schema never makes a file malformed, so turning a plugin off can't break the plugin's files.

### Malformed files

These files are malformed whether or not a plugin registered their type:

- Bytes that aren't UTF-8.
- Invalid YAML in the frontmatter.
- A frontmatter block with no closing `---` line.
- An `id` without a string `type`.
- An ID that doesn't match its type.

## Identity and revisions

Paths describe current locations. A move or rename does not change the frontmatter ID. The content revision is the BLAKE3 hash of the current file bytes. Update, move, and delete operations require the revision observed by the caller.

## Local metadata

`.noura/workspace.yaml` stores the workspace manifest. Deleting a file moves it to the operating system trash. When the system has no trash or refuses the move, the application moves the file to `.noura/trash/<timestamp>/<original-relative-path>` instead. Applications without an operating system trash, such as the browser build, always use that folder. `.noura/history/<object-id>/` stores Markdown snapshots that let you recover versions displaced during external-edit reconciliation. The note editor keeps its snapshots in `.noura/history/raw-<digest>/`. The digest is the first 16 hex digits of the BLAKE3 hash of the file's workspace-relative path. Each name is `<revision>-external.md` for a file version the editor replaced, or `<revision>-local.md` for a version of yours. Scanners ignore `.noura`, folders and files whose names start with a dot (such as `.obsidian` or `.DS_Store`), and top-level `node_modules` and `target` folders. They treat an iCloud placeholder such as `.Note.md.icloud` as the file `Note.md` that has not been downloaded yet. SQLite indexes, process locks, provider configuration, recent workspaces, and credentials do not belong in the workspace.

The application also writes these folders under `.noura`:

- `.noura/chat-mutations/`: one JSON intent file per chat change in progress. An intent holds the new bytes for a chat file and one message file. The application writes the intent before it changes those files and deletes it afterward. If an intent remains after a crash, the application writes its files the next time it reads the workspace.
- `.noura/sync/`: local state for encrypted sync, such as `config.json`, the `state.json` journal, validated key envelopes under `keys/`, and encrypted attachment blobs under `blobs/`. `plugin.json` records that this replica's `sync` plugin state was set once, so the application never turns the plugin back on after you turn it off. Only encrypted sync writes this folder. [Encrypted synchronization](sync-v1.md) defines its contents. The application never uploads it as a workspace file.
- `.noura/browser-storage/`: journals and staged writes for the browser build's workspace storage. Only the browser build writes this folder.

## Chats

Chats are durable managed Markdown. The application stores a newly created chat at `chats/<slug>--<chat-short-id>/chat.md`, where `chat-short-id` is the final six characters of the chat ULID. It stores messages beneath that directory at `messages/YYYY-MM-DD/chat-message_<ulid>.md`. Application writes always use this layout; stable IDs remain the identity if you move a file externally.

```markdown
---
id: chat_01j00000000000000000000000
type: chat
title: Release planning
retention: ephemeral
retention_days: 30
created: 2026-09-02T12:00:00Z
updated: 2026-09-02T12:00:00Z
---
```

Chats use `retention: ephemeral` with `retention_days: 30`, or `retention: permanent` with `retention_days: null`. A permanently retained chat may omit `retention_days`; readers treat the omission as `null` and writers serialize `null`. Local retention cleanup can move an ephemeral chat 30 days after creation. Retention moves only a fully valid, unchanged canonical chat directory to the trash, following the same rules as a deleted file; unknown files, malformed files, symlinks, moved chat directories, and files modified after expiry are retained.

```markdown
---
id: chat-message_01j00000000000000000000000
type: chat-message
chat_id: chat_01j00000000000000000000000
run_id: run_123
kind: tool-call
status: in-progress
content_type: application/json
provider_id: null
model_id: null
tool_call_id: call_123
tool_name: workspace.search
error_code: null
summarizes_through_message_id: null
created: 2026-09-02T12:01:00Z
updated: 2026-09-02T12:01:00Z
---

{"query":"release notes"}
```

Every message has `chat_id`, `run_id`, `kind`, `status`, and `content_type`. `run_id` must be non-empty after trimming and contain no control characters. Kinds are `user`, `assistant`, `tool-call`, `tool-result`, or `context-summary`; statuses are `in-progress`, `completed`, `interrupted`, `cancelled`, or `failed`. Assistant messages require `provider_id` and `model_id`; tool messages require `tool_call_id`, `tool_name`, `content_type: application/json`, and a deterministic JSON body. When present, provider, model, and tool metadata must be non-empty and contain no control characters. Failed messages require `error_code`; interrupted messages may include one. Other statuses omit it. An error code is at most 128 ASCII bytes and uses only letters, digits, dots, hyphens, or underscores. Context summaries require `summarizes_through_message_id`, which identifies a chat message. Fields not applicable to a kind may be `null` or omitted; readers treat omission as `null` and writers serialize `null`.

The application preserves unknown frontmatter properties on read-modify-write. Interrupted assistant messages recover as `interrupted`. An interrupted tool-call recovers as `completed` only when the same chat contains a completed durable tool-result with the same `run_id`, `tool_call_id`, and `tool_name`; otherwise it recovers as `interrupted`. Every append or finish request requires the current chat revision, and message finishes also require the current message revision. SQLite indexes derive the `chat_id` relation and are always rebuildable from these files.
